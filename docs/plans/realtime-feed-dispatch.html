Layers from connection setup to visible output

The shared responsibilities we can reuse, and the different runtime routes that exist today.

01 · Connect

Install a versioned connector; authenticate the source account; bind feed scope and device placement. Register provider deliveries or install an authorized browser observer where supported.

Connector declares provider processing.
Runtime owns secrets, grants and version binding.

02 · Receive

A clock requests collection, a provider posts a webhook, or an authorized observer buffers activity. These are different source adapters; a received hint is not yet a stored source event.

Connector owns observation.
Generic transport authenticates and preserves input.

03 · Execute

Resolve the scoped connector and claim durable work. Target: pull and delivered payloads invoke the same SDK/isolate lifecycle. Today native device executors and server webhook/chat adapters also exist.

Existing run lifecycle and isolate.
Retries and capacity checks remain shared.

04 · Obtain data

Connector code uses the supplied payload or requests missing data through authorized HTTP, browser or device capabilities. A complete WhatsApp message should not require another browser collection.

Provider parsing stays in connector code.
Host grants access to capabilities.

05 · Commit

Normalize source identity and event kinds; dedupe, persist, and activate matching Automations transactionally. Keep explicit receipt versus ingestion acknowledgments. Live reads and action results retain their existing result contracts.

One shared event ingestion path.
Source identity and exact revisions survive replay.

06 · React

Run the matching Automation or agent processing and execute its configured output. Browser notifications and provider replies use authorized actions. Interactive drafts still wait for human page activation and submission.

Existing Automation / conversation processing.
Existing connector action lifecycle.

07 · Recover

Retain unprocessed deliveries, retry failed work, reconcile source history after disconnects, and handle multiple arrivals while busy. Record receipt, isolate start, event commit and visible output separately.

Shared durable work and acknowledgment rules.

Current routes — the SDK consolidation is not shipped

Live reads / SQL / remote MCP

Caller → authorize configured source/tool → connector read in isolate or remote MCP execution → bounded rows/tool result → caller. These results do not automatically become feed events.

Action-only / output operations

Caller or Automation → existing action-mode and placement checks → isolate, browser, or native capability → action result → caller. Examples: market quotes, shell, computer use, and browser notifications.

What should become one path

Provider data push and pull should reuse connector isolate execution, capabilities, event output, persistence and declared Automation activation. A new provider on supported capabilities should require only a connector package.

Keep meaningful output distinctions

Feed events, live query results, action results and chat conversations have different contracts. Reuse the lower layers without forcing every operation into a feed. Native and chat SDK migration need their own parity evidence.

Current · hint, sync, browser reads, event

  1. Capture and preserve

    An initial sync binds the authorized page and installs the observer. A later message is stored with its revision in the extension’s bounded buffer.

  2. Collect and react

    The server marks the feed due. A worker runs the connector, requests browser reads, persists source events, and queues matching Automation runs.

  3. Acknowledge what succeeded

    The successful sync checkpoint acknowledges exact record revisions. The extension removes those revisions only after receiving the saved acknowledgment.

Receipt ≠ successful ingestion

“The feed is scheduled” cannot authorize deleting a buffered message. Unacknowledged records remain available for replay. Dedupe uses the connection and source origin_id.

Two independent directions

The extension sends a source hint to the server immediately. Separately, a worker waits to receive a job. Source hints must continue while a job request is held; the existing zero-capacity notification path can support that.

Timeout and recovery

If nothing arrives, the server returns at the bound and the worker opens another request. A missed notification leaves the durable work in Postgres for recovery. Scope, capacity, device affinity, and approvals still apply.

Five concepts we already have

ConceptPlain meaning
ConnectionWhich account or device we may access.
FeedWhich source data to collect, with its scope and checkpoint.
RunA durable unit of work waiting to execute, executing, or completed.
EventA persisted source record, identified across syncs by connection + origin_id.
AutomationA configured reaction: match a trigger, execute, and produce an output.

Evidence needed before calling it realtime

  1. Prove collection is optional

    A complete payload invokes the isolate, emits an event, and activates without a browser reread. Incomplete hints still collect. Prove an external connector bundle can do both without core edits.

  2. Prove durable recovery

    Cross-replica notifications, concurrent claims, busy workers, reconnects, lost signals, and exact-revision acknowledgments.

  3. Repeat the real flows

    WhatsApp self-message to visible notification, GitHub trigger delivery, and direct-store Automation parity. A target under 1 second applies to idle dispatch.

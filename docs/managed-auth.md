# Managed auth — a local install using a cloud-held OAuth grant

A local Lobu install cannot complete a Google (or most provider) OAuth flow on
its own. The connector connect flow redirects to `<base>/connect/oauth/callback`,
and that URI is not registered on the provider's OAuth client for any localhost
port — only the hosted origin is. The handshake dies at
`Error 400: redirect_uri_mismatch`.

**Managed auth is the supported answer, and it needs no connector code.** The
grant lives in a cloud (public) org whose redirect *is* registered; the local
instance fetches a short-lived access token for it at runtime and runs the
connector locally against local Postgres.

Do not reach for a Google Cloud Console redirect edit, a service-account
impersonation, or a hand-minted token before checking whether the connector is
offered as managed.

## The two halves

### 1. Get the grant (once, in the cloud)

`manage_connections action: connect_managed` — SDK `connections.connectManaged`
— joins the public org that publishes the connector plus an active `oauth_app`
profile, then runs the ordinary connect flow inside that org. The resulting
connection is a *consent-only grant holder*: it carries the OAuth grant and has
no feeds, so the cloud never syncs the user's data.

`client.organizations.list` reports which connectors an org offers
(`credential_mode: managed`, `connect_method: connections.connectManaged`).
A connector gains managed auth by being added to a public org's offer — there is
no `managedBy` declaration in connector source.

### 2. Use it (every run, locally)

The local connection opts in through its **config**, not through the connector:

```ts
defineConnection({
  slug: "gmail",
  connector: "google.gmail",
  credentialMode: "managed",
  managedBy: { org: "lobu-cloud", connectionSlug: "gmail-abc123" },
  feeds: [...],
})
```

`connectionSlug` names the exact caller-owned cloud grant and is generated by
`lobu init --from-org <slug>`. It is optional only so older single-grant configs
keep working; omit it and a user with two accounts gets an arbitrary one.

At execution, `resolveManagedByForConnection` reads `config.managedBy` and
`fetchManagedConnectionToken` POSTs to the cloud's `/oauth/connection-token`,
receiving only `{ access_token, expires_at }`. The connector then runs locally.

## The security shape (do not "fix" these)

- **The bearer token and the cloud base URL come only from the local install's
  own login** (`resolveCloudCredential`: `~/.config/lobu/credentials.json`,
  falling back to `LOBU_CLOUD_PAT` + `LOBU_CLOUD_URL` for headless/CI). The
  connection config supplies the `org` and nothing else. A connection-controlled
  URL would let a malicious config exfiltrate the cloud credential.
- The login token must carry the **`connections:token`** scope. It is granted on
  the device-code login path or an explicitly minted PAT, never the auth-code
  path.
- Resolution is **fail-soft**: a failed token fetch returns null credentials and
  the connection surfaces an auth error, rather than throwing.

## Why your token fetch 404s

`/oauth/connection-token` returns the same not-found shape unless **all three**
hold, so it never leaks which one failed:

1. the connection is the caller's own (`created_by`),
2. its org is **public** (`organization.visibility = 'public'`),
3. it is a consent-only grant holder (`config.consent_only = 'true'`).

A grant in your own personal workspace therefore cannot be delegated to a local
install, by design — the endpoint exists only to delegate managed grant holders,
never to export ordinary connection tokens. A missing `connections:token` scope
fails earlier, as a 403 `insufficient_scope`.

## If the connector is not offered as managed

Then there is no managed path, and adding one is a product decision (it publishes
the connector to everyone who joins that public org, under Lobu's OAuth client,
with whatever verification tier its scopes demand). For local development
against such a connector, register the local callback on the provider's client
instead:

```
PUBLIC_GATEWAY_URL=http://localhost:3000 PORT=3000 make dev
```

`resolveBaseUrl` prefers `PUBLIC_GATEWAY_URL` over the request Host, so this
pins the redirect to a URI you can register once
(`http://localhost:3000/connect/oauth/callback`).

To test whether a redirect URI is registered, read the **Location header** of the
authorize request, not the body — a mismatch 302s to
`accounts.google.com/signin/oauth/error` with a base64 `authError` that decodes
to `redirect_uri_mismatch`. Body-grepping finds nothing and silently reports
every URI as valid, so always include a known-bad negative control.

## Proving a change

`scripts/managed-e2e.sh` boots two real `lobu run` instances plus mock OAuth and
data servers and exercises cloud-auth/local-data over real HTTP. Use it rather
than hand-wiring a token.
